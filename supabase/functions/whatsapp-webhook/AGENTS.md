# whatsapp-webhook rules
- whatsapp-webhook acts only on the newest message: history is sent dated and labelled as already handled, every save tool call is grounding-checked against the latest message (blocked calls logged as `ungrounded_save_blocked`), tool rounds loop up to 5, and replies announcing future actions are replaced with a code-built summary — why: old history requests were being re-saved and promised saves weren't happening.
- Reply timing for saved items comes from a code-computed TIMING line in the tool result — why: the model miscalculated the 6pm/7am rules.
- Unclear saves become a stored question, not a refusal: `ask_parent_to_confirm` / the which-child rule store `conversations.context.pending_action` (24h expiry, dropped on topic change) and `tryResolvePendingAction` saves on "yes"/a name/"both"; every save goes through `runSave`, and replies are checked for system wording and vague failures — why: parents must never see internal markers or a flat "NOT SAVED".
- One-off vs weekly is decided in code (`decideSave` in whatsapp-webhook): already covered by an active weekly reminder → nothing saved, "already on the list"; recurring words → weekly reminder; one-off signals → dated note; otherwise ask "just <day>, or every <weekday>?" via a `frequency` pending action — why: the model silently turned one-offs into weekly reminders.
- Children are always named in replies and stored summaries (`nameNotPronoun` on every reply, plus a prompt rule) — why: Monty doesn't know genders and must never guess.
- Day moves ("X has moved to Wednesday") are handled in code by `tryMoveReminder` before the AI: one matching active weekly reminder → its own row's day_of_week is updated; several or none → one question (`move`/`confirm` pending action) — why: the model sometimes left the old day active or created a second row.
- When both the child and one-off vs weekly are unclear, one combined question is asked (`ask_frequency` on the pending action) and both answers are parsed from one reply; a partial answer keeps the pending item and asks only for the missing part — why: parents were asked two questions in a row.
- Save confirmations are one code-built line (`confirmationLine`) from actual save results, with no reminder-timing text; the suite fails any confirmation that isn't one line under 120 characters naming the child — why: Matt wants short, always-accurate confirmations.
- Every outgoing webhook reply passes `applyContactGuard` (`_shared/contactGuard.ts`): emails, web addresses and phone numbers must be Monty's own, stored for the parent's school, or in the parent's latest message; anything else is cut and replaced with an honest line, logged as `invented_contact_blocked` — why: the model invented support and school contact details.
- The "haven't saved anything yet" fallback is used only when the parent's latest message looks like a save request (`SAVE_REQUEST`); otherwise the future-action sentences are dropped and the rest of the reply kept — why: plain updates were getting a confusing failure reply.
- AI calls use max_tokens 2000: the model can spend its budget on hidden thinking; at 500, multi-item messages ended with stop_reason max_tokens, no text or tool call, and got the outage reply. Cost is per token used, not the limit.
- A save held because it overlaps an existing school event, reminder or note is stored as a `duplicate` pending action (held item + matching item) via `holdDuplicate`; the answer is resolved in `resolveDuplicatePending` without re-running the duplicate check ("yes"/"different"/"save it" → one-off note with the parent's wording; "no"/"same one" → one-off note with the existing title, because school events don't trigger reminders yet; anything else → dropped). If the same question would be asked twice in a row for the same item (`last_dup_question`, 1h), the item is saved instead — why: an unstored duplicate question fell back to "which child?" and looped three times with nothing saved.
- A save held as overlapping a SCHOOL EVENT is saved directly (under the event's title, code-built "That's … from school. I've added it to <child>'s reminders for <day> ✅") when the event's year group (stored `school_events.year_group`; a stored "all"/blank is only narrowed by a KS1/KS2/EYFS title, otherwise it is not a clear match) includes the child's via `yearGroupMatches` from `_shared/schoolEventRules.ts` and a non-generic topic word is shared between the event title and the parent's OWN message (never the AI's summary, which can copy the event's wording) (`clearSchoolEventMatch`); otherwise (other or unknown year, only generic words, or a note/reminder match) the stored "different one?" question is asked — why: no needless questions, but real doubt is still checked. Test events must be seeded with a real year_group.
- When several existing items overlap a save, the duplicate check uses the one sharing the most words with the parent's message + summary (ties → first found) — why: "Y3/4 Mixed…" and "Y3/4 Girls Football Tournament" fall on the same day.
